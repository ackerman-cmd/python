## Архитектура

| Свойство | Реализация |
|---|---|
| Независимость домена | Только стандартная библиотека и собственные доменные модули |
| Сценарии приложения | Зависят от domain и портов application |
| Входная граница | Строгий Pydantic DTO преобразуется в независимый доменный объект |
| Неизменяемость | Frozen dataclass, вложенная frozen декларация, tuple для коллекций |
| Валидация | Общие чистые проверки используются DTO и доменными конструкторами |
| Композиция | Репозиторий и реестр передаются через конструкторы |
| Расширяемость | Анализаторы подключаются фабриками без изменения сервиса |
| Ошибки плагина | Явный AnalysisFailure с сохранённой причиной |
| Проверка результата | Структура, хеши, метаданные, объяснения, score и evidence |
| Ресурсы | Владение файлом у контекстного менеджера источника |
| Сборка | Отдельные зависимости каждого приложения создаёт bootstrap |
| Запуск | Console script и python -m school_lab; импорт не запускает обработку |

Зависимость AnalysisService от простого AnalyzerRegistry внутри application соответствует
масштабу синхронного приложения. Реестр не связывает сервис с конкретными классами анализаторов.
Подробное описание контрактов и решений приведено в docs/ARCHITECTURE.md.

## Тестовые сценарии

Unit-проверки охватывают строгие поля и типы, вложенную декларацию, прямое создание домена,
UTF-8, устойчивый хеш между процессами, подсчёт строк, точные блоки шаблона и форму отчёта.

Контрактные проверки повторяются для двух источников и четырёх анализаторов. Проверяются
порядок, изоляция записей, отрицательный контекст задания, неизменность исходника,
повторяемость наблюдений, связь с конфигурацией и исходные диапазоны evidence.

Интеграционные проверки охватывают accepted/duplicate/conflict, частичный импорт,
анализ через реестр, третью регистрацию, CLI и невыполнение принятого Python-кода.

Отдельные отрицательные сценарии:

- Повреждённый JSON, повторный ключ, NaN/Infinity, большое число и глубокая вложенность.
- Пустая строка, неизвестные поля, нестроковые ключи, неверная дата и AI-декларация.
- Unicode-суррогаты в содержимом, ключах и конфигурации; сохранение обычного Unicode и emoji.
- Закрытие файла при завершении, break, исключении потребителя и отказе декодирования.
- CRLF, слишком длинная последняя строка без newline и неверный лимит источника.
- Отказ фабрики и properties интерфейса, неверные метаданные и отсутствие callable analyze.
- Ожидаемый и неожиданный отказ анализатора, неправильный тип результата.
- Недопустимый score, unknown kind, неправильная коллекция или элемент evidence.
- Evidence вне границ исходника, чужая сдача и несовместимый config_hash.
- Пустой корпус, отсутствующее задание, неверная конфигурация и аргументы CLI.

## Методика оценки покрытия

В `coverage.json` учитываются исходники `school_lab`, включая CLI, bootstrap и примеры;
тестовые файлы не входят в знаменатель. Под покрытием строк здесь понимается исполнение
операторов, учитываемых coverage, а не доля физических строк файла.

Покрытие операторов вычислено как `831 / 832 × 100`, ветвей — как `162 / 162 × 100`.
Суммарная метрика вычислена как `(831 + 162) / (832 + 162) × 100`; это не среднее
арифметическое двух процентов. Порог 90% в `pyproject.toml` относится к суммарной метрике.

Агрегация сохранённого результата по пакетам:

| Область | Покрытые операторы | Покрытые ветви |
|---|---:|---:|
| `domain` | 158/158 | 26/26 |
| `application` | 153/153 | 54/54 |
| `adapters` | 239/239 | 32/32 |
| `analyzers` | 59/59 | 6/6 |
| `interfaces` | 52/52 | 8/8 |
| `examples` | 80/81 | 18/18 |
| Корневые модули пакета, включая bootstrap | 90/90 | 18/18 |
| **Всего** | **831/832** | **162/162** |

Пустые `__init__.py` не добавляют операторов. Непокрытый путь расположен в примере,
а не в обработке DTO, сервисе, источнике или валидации отчёта. Стандартные исключения
coverage для протокольных объявлений остаются частью методики и не скрываются итоговой цифрой.

## Содержательная полнота тестов

| Файл | Основной проверяемый контракт | Проверяемые последствия |
|---|---|---|
| `test_acceptance.py` | DTO, домен, приём и хеш | Ошибка поля, исходный словарь не изменён, конфликт не перезаписал объект |
| `test_sources.py` | Источники, строгий JSON и ресурсы | Порядок, повторное открытие, изоляция копий, закрытие handle |
| `test_analyzers.py` | Алгоритмы и проверка отчёта | Строки, точные блоки, стабильные наблюдения, метаданные и диапазоны |
| `test_application.py` | Сборка и интеграция | Ранний отказ конфигурации, независимость приложений, замена источника и CLI |
| `test_boundaries.py` | Граничные входы и интерфейс | CRLF, EOF, лимит, неверная UTF-8, прямые конструкторы, entrypoints |
| `test_regressions.py` | Пределы парсера, Unicode и плагины | Продолжение импорта, безопасная диагностика, сохранённая причина отказа |
| `test_plugin_failures.py` | Ожидаемый отказ расширения | Исходное исключение передано, принятая работа сохранена |

185 — число выполненных случаев с учётом параметризации, а не число отдельных функций.
Параметризация нужна для одинаковой проверки нескольких источников, анализаторов и
отрицательных входов. Основные утверждения проверяют наблюдаемое поведение: возврат прежнего
объекта при дубликате, отсутствие перезаписи, принятие следующей строки, исходную нумерацию
evidence и сохранность ресурса. Одного утверждения об отсутствии исключения было бы недостаточно.

Проверка повторяемости отчётов отделяет смысловые поля от UUID и времени. Проверка упаковки
отделена от editable-установки, а тест невыполнения принятого кода использует наблюдаемый
побочный эффект, который не должен возникать. Эти сценарии защищают свойства, способные
нарушиться при внешне правдоподобной реализации.

## Архитектурное качество и компромиссы

Домен содержит только данные и чистые правила, сервисы координируют операции, адаптеры
работают с внешним представлением. Разделение не основано на количестве строк в файле:
каждый пакет имеет отдельную причину изменения. Например, новая схема ввода затрагивает
DTO, новый способ чтения — источник, а новый алгоритм — реализацию Analyzer.

Входная валидация и доменные инварианты используют общие функции. Это сохраняет защиту
прямых конструкторов и уменьшает риск расхождения правил. Реестр расположен в application
и содержит фабрики, а не конкретные классы; зависимость сервиса от него остаётся внутри слоя.
Явная сборка позволяет подменять порты без глобального состояния.

Есть сознательные компромиссы. Репозиторий повторно хеширует сохранённую работу, что
упрощает модель за счёт дополнительной линейной операции. Поиск шаблона сравнивает блоки
строк напрямую, поскольку контракт требует точных совпадений. Возвращается первая ошибка
валидации, а не агрегированный список всех нарушений. Эти решения соответствуют учебному
объёму и описанному публичному поведению.

Статический граф подтверждает направления найденных импортов, но не устанавливает
качество каждой функции и не доказывает отсутствие динамических связей в любом будущем
расширении. Поведенческие выводы опираются на перечисленные тесты и ревью контрактов.

## Связь результатов и пределы проверки

Проверки стиля, типов, покрытия и интеграции отвечают на разные вопросы. Ruff выявляет
нарушения выбранных правил, mypy — несовместимые типы в аннотированном коде, pytest —
нарушения заданных сценариев, coverage — исполненные пути. Успех одного инструмента
не подменяет результаты остальных.

Не проводились нагрузочные испытания многопоточного сервера, аудит изоляции недоверенных
плагинов, mutation testing и исчерпывающий перебор входных данных. Таких гарантий у проекта
нет. Для имеющихся синхронных сценариев существенных незакрытых замечаний ревью не осталось;
известные ограничения перечислены в [REPORT.md](REPORT.md).

Результаты проверок — сохранённый снимок версии кода. Назначение файлов и условия
воспроизведения описаны в [evidence/README.md](evidence/README.md), команды — в
[README](../README.md). При изменении логики прежний снимок не доказывает корректность
новой реализации.
