# Контракты данных и Python API

Документ описывает текущую схему версии 1. Приём и анализ — отдельные операции:
работа может быть сохранена до загрузки задания, но анализ требует подходящего `Assignment`.
Полный маршрут компонентов приведён в [архитектуре](ARCHITECTURE.md).

## Входная работа

Все ключи объекта `SubmissionInput` обязательны. Лишние поля запрещены на обоих уровнях,
типы проверяются строго. Таблица описывает JSON-вход; после валидации он преобразуется
в независимый `Submission`.

| Поле | Тип JSON | Правило |
|---|---|---|
| `schema_version` | integer | Только 1; `true` и строка `"1"` не подходят |
| `submission_id` | string | Непустой идентификатор версии |
| `student_id` | string | Непустой идентификатор студента |
| `assignment_id` | string | Непустой идентификатор задания |
| `submitted_at` | string | ISO 8601, распознаваемый `datetime.fromisoformat`, с часовым поясом |
| `text` | string | Может быть пустым, если непустой `code` |
| `code` | string | Может быть пустым, если непустой `text` |
| `template_id` | string или null | Непустая строка либо явно переданный `null` |
| `ai_declaration` | object | Вложенная декларация по следующей таблице |

| Поле декларации | Тип JSON | Правило |
|---|---|---|
| `used` | boolean | Использование ИИ заявлено или не заявлено |
| `tool` | string или null | При `used=true` обязательна непустая строка |
| `purpose` | string или null | При `used=true` обязательна непустая строка |
| `verified_by_student` | boolean | Подтверждение проверки результата студентом |

При `used=false` поля `tool` и `purpose` также присутствуют: допустимы `null` или непустые
строки. Отсутствующий ключ отличается от ключа со значением `null`. Пустота проверяется
через `strip()`, но принятое значение не обрезается. Все строки должны кодироваться в UTF-8.

Пример корректного объекта:

```json
{
  "schema_version": 1,
  "submission_id": "example-001",
  "student_id": "student-001",
  "assignment_id": "assignment-01",
  "submitted_at": "2026-10-14T12:00:00+03:00",
  "text": "Функция возвращает сумму элементов.",
  "code": "def solve(values):\n    return sum(values)\n",
  "template_id": null,
  "ai_declaration": {
    "used": false,
    "tool": null,
    "purpose": null,
    "verified_by_student": true
  }
}
```

В JSONL каждый такой объект записывается в одну физическую строку. Переводы строк
внутри `text` и `code` представлены escape-последовательностью `\n`.
Пустая физическая строка является ошибкой записи. JSON с повторными ключами,
`NaN` или `Infinity` не допускается.

## Результат приёма и состояние

`AcceptanceAdapter.accept_payload(raw)` принимает Python-объект после декодирования JSON.
Возвращаемый `Acceptance` содержит `status`, принятую `submission` и `submission_hash`;
свойство `submission_id` возвращает ID доменного объекта.

| Вход относительно репозитория | Результат | Состояние |
|---|---|---|
| ID отсутствует | `accepted` | Работа добавлена |
| ID существует, хеш совпадает | `duplicate` | Возвращён прежний объект |
| ID существует, хеш отличается | Исключение `SubmissionError`, код `conflict` | Прежний объект сохранён |
| Ошибка схемы | Исключение `SubmissionError` | Новая работа не добавлена |

`conflict` не является третьим значением `Acceptance.status`: это отказ операции.
Изменённая работа принимается под новым `submission_id`. Хеш включает все поля сдачи,
поэтому изменение только декларации или времени при прежнем ID тоже создаёт конфликт.

Приём не проверяет существование задания и не сопоставляет `template_id` с каталогом шаблонов.
Для анализа используется `context.assignment.allowed_template`; `template_id` сохраняется
как метаданные сдачи.

## Импорт и источники

`SubmissionSource.open()` возвращает контекстный менеджер итератора `SourceRecord`.
Запись содержит `line_no`, `raw` или `error`. У JSONL `line_no` — физический номер строки,
у источника в памяти — позиция элемента от 1.

`import_source(source, adapter)` возвращает `ImportSummary`. В JSON-представлении
`accepted` и `duplicate` — списки ID, `errors` — список диагностик с `line_no`:

```json
{
  "accepted": ["example-001"],
  "duplicate": ["example-001"],
  "errors": [
    {
      "line_no": 3,
      "code": "conflict",
      "field": "submission_id",
      "message": "ID уже связан с другой версией"
    }
  ]
}
```

Один ID может встречаться в обоих списках, если сначала принят, а затем повторён в том же
источнике. Это журнал исходов, а не два непересекающихся множества объектов.
Ошибка записи допускает продолжение; отказ открытия или декодирования UTF-8 прерывает импорт.
Уже сохранённые работы остаются в репозитории. При таком отказе CLI выводит диагностику,
а не частичный `ImportSummary`.

## Задание и конфигурация

`load_assignments(path)` читает непустой JSON-массив заданий. Каждый объект содержит
`assignment_id`, `allowed_template` и `requirements`. Идентификаторы уникальны,
требования — список непустых строк; в домене он преобразуется в `tuple`.
Сам список требований может быть пустым. Текущие анализаторы не проверяют выполнение
каждого требования: они сохраняются в контексте и участвуют в `config_hash`.

Конфигурация приложения:

```json
{
  "config_version": "1",
  "analyzers": [
    {"name": "length", "params": {}},
    {"name": "template", "params": {}}
  ]
}
```

При `build_application()` применяются эти значения по умолчанию. `params` можно опустить;
текущие реализации допускают только пустой словарь. Список анализаторов должен быть
непустым, без повторов и с известными именами. `config_version` — непустая строка.
Дополнительные классы регистрируются через Python API; имена `declaration` и
`missing-explanation` не входят в список фабрик загрузчика JSON-конфигурации.

## Контракт анализа

`AnalysisService.run(submission_id, analyzer_name, context)` возвращает `AnalysisReport`.
Работа должна быть принята, а ID задания в ней должен совпадать с ID в контексте.
Реестр создаёт экземпляр анализатора при каждом `run`; фабрика вызывается без аргументов.

| Поле отчёта | Назначение и проверка |
|---|---|
| `report_id` | Непустой ID запуска; `make_report` по умолчанию создаёт UUID |
| `submission_id`, `submission_hash` | Ссылка на именно эту версию принятой работы |
| `analyzer_id`, `analyzer_version` | Непустые метаданные, совпадающие с вызванной реализацией |
| `config_hash` | SHA-256 задания и версии конфигурации |
| `findings` | Непустой `tuple` объектов `Finding` |
| `created_at` | Время с часовым поясом; фабрика использует UTC |
| `review_required` | Строгий `bool`: требуется ли ручное рассмотрение |

Наблюдение `Finding` содержит `kind`, `score`, `evidence`, `explanation`. Допустимые виды —
`similarity`, `rubric_feedback`, `processing_error`. `score` — конечное число в [0, 1]
или `None`, но не `bool`; текущие анализаторы возвращают `None`. Объяснение непустое,
`evidence` — `tuple`, который может быть пустым.

Каждый `Evidence` ссылается на ту же сдачу, поле `text` или `code` и включительный диапазон
строк `1 ≤ start_line ≤ end_line ≤ число строк`. Нумерация использует исходное
`splitlines()`: пустые строки не удаляются и номера не сдвигаются. После сериализации
кортежи представлены JSON-массивами.

## Ошибки и CLI

| Код | Значение | Реакция |
|---|---|---|
| `invalid_json` | JSON повреждён или запись превышает пределы | Ошибка записи, продолжение |
| `schema_error` | Структура, типы или инварианты не соблюдены | Ошибка записи, продолжение |
| `unsupported_version` | Целочисленная версия схемы отличается от 1 | Ошибка записи, продолжение |
| `conflict` | ID уже связан с другой версией | Ошибка записи, сохранение оригинала |
| `configuration_error` | Конфигурация или каталог заданий некорректны | Отказ запуска сценария |
| `analysis_error` | Отказ поиска, фабрики, анализатора или проверки отчёта | Отказ анализа |
| `source_error` | Файл недоступен или не декодируется | Диагностика CLI, завершение |

Общий формат — `code`, `field`, `message`. Импорт добавляет `line_no`.
`source_error` формируется интерфейсом из исключения ввода-вывода; в Python API сохраняется
`OSError` или `UnicodeError`. Ошибка анализатора сохраняет причину через цепочку исключений.

CLI выводит результат в stdout и диагностику запуска в stderr. Код 0 означает успешную
команду, 1 — завершённый импорт с ошибками записей, 2 — отказ источника, конфигурации,
анализа или аргументов. Для ошибок разбора аргументов argparse выводит обычную справку
и текст ошибки, а не JSON. Сценарий `demo` специально содержит ожидаемые отказы и при
успешной демонстрации возвращает 0.
