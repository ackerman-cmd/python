# Лабораторная работа 1. Приём работ и расширяемые анализаторы

**Траектория:** Backend. **Уровень:** основной и углубление Backend.
**Дата выполнения проверок:** 14 октября 2026 года.

Отчёт содержит технические решения и фактические результаты для письменной защиты.
Использование инструментов ИИ описано в AI_USAGE.md. Команды воспроизведения приведены
в README и в разделе проверки.

## 1. Цель и границы работы

Разработана основа системы онлайн-школы, принимающая версии студенческих работ и запускающая
заменяемые анализаторы. Цель — освоить строгую валидацию, устройство Python-пакета,
неизменяемые модели, композицию, Protocol, работу с ресурсами и тестирование контрактов.

Выполнение синхронное, репозиторий находится в памяти процесса. Исходный Python-код принятой
работы анализируется как строка: импортировать или исполнять его не требуется. База данных,
HTTP-сервер, ORM, очередь и реальная модель ИИ в работу не включены. Backend-вариант реализован
через Pydantic DTO и тестовый адаптер, независимый от HTTP.

Контракт данных и границы реализации определены заданием ЛР 1 и материалами лекции.
data/submissions.jsonl содержит 12 учебных записей PUBLIC_SUBMISSIONS. assignments.json
описывает демонстрационное задание, а invalid_submissions.jsonl содержит смешанный сценарий
импорта. Корпус используется для воспроизводимых проверок и не содержит реальных работ студентов.

## 2. Архитектура Backend-варианта

Исходники распределены по шести пакетам: domain (модели и инварианты), application
(порты и сценарии), adapters (DTO, источники и хранилище), analyzers (конкретные расширения),
interfaces (CLI) и examples (демонстрация и измерение). bootstrap.py — точка сборки.
Контракты Analyzer, SubmissionRepository, SubmissionSource и SourceRecord находятся
в application/ports.py. Application не импортирует реализации из adapters/analyzers.
Пакет запускается через python -m school_lab либо console script school-lab.


```text
JsonlSource / InMemorySource
        ↓
SourceRecord: номер строки, объект или ошибка JSON
        ↓
AcceptanceAdapter.accept_payload
        ↓
SubmissionInput → Submission
        ↓
SubmissionService → SubmissionRepository
        ↓
AnalysisService → AnalyzerRegistry → Analyzer.analyze
        ↓
validate_report → AnalysisReport
```

| Компонент | Ответственность |
|---|---|
| DTO Pydantic | Проверяет внешнюю структуру, типы, поля и зависимости между ними |
| Submission | Представляет неизменяемую версию работы, защищает доменные инварианты |
| AcceptanceAdapter | Преобразует DTO в домен и вызывает сервис |
| SubmissionService | Различает принятие, дубликат и конфликт |
| Repository | Хранит версии, не перезаписывает конфликтующую запись |
| Источник | Читает записи, сохраняет физические номера строк и управляет ресурсом |
| Импортёр | Собирает accepted, duplicate и errors, продолжает после ошибки записи |
| AnalysisService | Получает сдачу, выбирает анализатор из реестра, проверяет результат |
| Анализатор | Формирует наблюдения по единому контракту |
| build_application | Создаёт зависимости и проверяет конфигурацию |
| CLI | Разбирает аргументы, выводит JSON и задаёт код завершения |

Домен и сервисы не импортируют Pydantic, FastAPI или ORM. Внешняя ошибка Pydantic переводится
в SubmissionError с полями code, field, message. HTTP-статус мог бы назначить будущий адаптер;
доменное исключение не содержит HTTP-семантики.

Каждое приложение получает собственный репозиторий и реестр. Глобальные изменяемые
экземпляры не используются. Зависимости передаются через конструкторы. В тесте источник
заменяется InMemorySource без изменения сервиса или глобальной подмены его функций.

## 3. Приём и валидация — этап А

SubmissionInput и DeclarationInput настроены с strict=True, extra="forbid", frozen=True.
Строка "false" не превращается в True, число не превращается в строковый ID, неизвестные
поля не исчезают. Все ключи схемы обязательны; nullable-поле отличается от отсутствующего.

Проверяются следующие инварианты:

- schema_version — int со значением 1; bool как версия отклоняется;
- submission_id, student_id и assignment_id — непустые строки;
- submitted_at — ISO 8601, поддерживаемый datetime.fromisoformat, с часовым поясом;
- хотя бы одно из text и code непустое после проверки strip();
- template_id — непустая строка либо null;
- used и verified_by_student — строгие bool;
- при used=true tool и purpose должны быть непустыми строками.

Валидация использует общие чистые функции validation.py. DTO оборачивает ожидаемые доменные
нарушения в ошибки Pydantic, а адаптер возвращает стабильный контракт ошибки. При нескольких
нарушениях возвращается первое в порядке валидации. Версия 2 отклоняется с отдельным кодом
unsupported_version, остальные нарушения схемы — schema_error.

Метод DTO.to_domain создаёт frozen dataclass Submission с вложенной frozen AIDeclaration.
Все её поля — неизменяемые значения; коллекции отчётов — tuple. В отличие от поверхностно
замороженного объекта со списком, обычное изменение вложенных данных здесь запрещено.
__post_init__ дополнительно проверяет инварианты при прямом создании доменного объекта.

Входные словари не изменяются. Пробелы и переводы строк text/code сохраняются. submitted_at
тоже сохраняется исходной строкой после проверки. strip() используется только для проверки
пустоты. Это сохраняет соответствие между evidence и исходным содержимым.

### Отпечаток версии и повторный приём

SHA-256 вычисляется от UTF-8 JSON всей сдачи с параметрами sort_keys=True,
separators=(",", ":"), ensure_ascii=False, allow_nan=False. Порядок ключей словаря не влияет
на результат. Перевод строки, декларация или идентификатор влияют. Время анализа и путь
импортируемого файла не входят в отпечаток.

Встроенный hash() предназначен для структур данных Python и для строк зависит от процесса;
его нельзя применять для устойчивого отпечатка сдачи. Это проверено отдельными процессами
с разными PYTHONHASHSEED. SHA-256 также не доказывает авторство и не обнаруживает частичное
сходство решений.

| Условие | Результат | Изменение репозитория |
|---|---|---|
| Новый submission_id | accepted | Добавляется версия |
| Прежний ID и тот же хеш | duplicate | Не меняется; возвращается сохранённый объект |
| Прежний ID и другой хеш | conflict | Прежняя версия остаётся |
| Изменённая работа с новым ID | accepted | Добавляется новая версия |

Сам репозиторий тоже отказывается перезаписывать конфликтующую запись. Однако последовательность
get/add не является транзакцией для нескольких потоков; поддерживается последовательный режим ЛР 1.

## 4. Источники, ресурсы и частичный успех — этап Б

Оба обязательных источника реализуют open(), возвращающий контекстный менеджер итератора
SourceRecord. Контрактные тесты проверяют порядок, номера записей, повторное открытие и
изоляцию данных. InMemorySource копирует вход и выдаёт независимые копии.

JsonlSource владеет файлом и закрывает его после выхода из with, включая break и исключение
потребителя. Сам break завершает цикл, но не гарантирует финализацию произвольного генератора;
поэтому владение файлом вынесено в контекстный менеджер. После выхода закрывается и итератор.

decode_json отделён от проверки схемы. Повреждённый JSON, повторный ключ, NaN, Infinity и
пустая физическая строка дают invalid_json. Источник ограничивает длину физической строки
1 000 000 символами, включая перевод строки, и дочитывает превышение ограниченными порциями.
Номер следующей записи сохраняется. Невозможность открыть файл или неверная UTF-8-кодировка
является ошибкой источника, а не ошибкой отдельной схемы.

Импорт атомарен на уровне одной записи: корректные записи до ошибки сохраняются.
Импортёр перехватывает ожидаемый SubmissionError, записывает номер строки и продолжает.
Неожиданные дефекты приложения не превращаются молча в успешный импорт.

Дополнительный StreamSource для io.StringIO не закрывает переданный поток. Его владельцем
остаётся вызывающий код, а повторное открытие начинает чтение с текущей позиции. Это
отдельно указанный ресурсный контракт, а не полностью идентичное поведение файлового источника.

## 5. Анализаторы, отчёт и расширение

Контракт Analyzer описан через Protocol: analyze(submission, context) → AnalysisReport.
Context содержит Assignment и config_version. Структурная совместимость позволяет классу
реализовать методы без наследования от Protocol. Наследование могло бы передавать общую
реализацию, но само по себе тоже не доказывает корректность поведения.

LengthAnalyzer считает непустые строки text и code отдельно. Комментарий является непустой
строкой. Результат имеет kind=rubric_feedback, score=null и пояснение, что количество строк
не измеряет правильность решения.

TemplateAnalyzer ищет точные непрерывные блоки полных строк разрешённого шаблона Assignment.
Пробелы не нормализуются, пустой/пробельный шаблон не считается совпадением. Найденные
диапазоны возвращаются как similarity, score=null с пояснением о разрешённом совпадении.
Переименование переменных и нечёткое сходство этим анализатором не обнаруживаются.

AnalysisReport содержит report_id, submission_id, submission_hash, analyzer_id,
analyzer_version, config_hash, findings, created_at и review_required. Evidence содержит
ID сдачи, поле text/code и включительный диапазон исходных строк с нумерацией от 1.

validate_report проверяет структуру результата, привязку к сдаче и конфигурации,
метаданные, время с зоной, объяснения, score и диапазоны evidence. True не является score,
NaN/Infinity и значения вне [0, 1] отклоняются. Сервис дополнительно сверяет метаданные
результата с вызванным анализатором. Ошибка плагина переводится в явный AnalysisFailure с
сохранением причины через raise ... from; исходная сдача остаётся неизменной.

config_hash включает задание целиком и версию конфигурации. Изменение шаблона или версии
меняет хеш; прежний отчёт не принимается как результат новой конфигурации. UUID и время
запуска могут различаться, поэтому повторяемость проверяется по смысловым findings и хешам.
Для точных unit-проверок фабрика ID и часы передаются в make_report явно.

### Дополнительный анализатор декларации

В extensions.py реализован DeclarationAnalyzer. Подключение:

```python
app.registry.register("declaration", DeclarationAnalyzer)
```

Уже собранный AnalysisService не изменяется. В docs/evidence/demo.json зафиксированы
extension.same_service=true и имена length, template, declaration.

Неполная декларация при used=true отклоняется ещё при приёме. Анализатор описывает принятую
декларацию и выставляет review_required, если использование ИИ заявлено, а студент не
подтвердил проверку результата. Он не устанавливает происхождение текста. Проверка неполной
декларации не переносилась из DTO в анализатор ради демонстрации расширения.

Дополнительно выполнено упражнение MissingExplanationAnalyzer: код без непустого text
получает объяснение и review_required=true, score=null. Для всех четырёх анализаторов
запускается общий набор контрактных тестов.

## 6. Углубление Backend

build_application(config) собирает репозиторий, реестр, сервисы и адаптер. Конфигурация
проверяется до первого вызова accept_payload или run. Отклоняются неизвестный анализатор,
повтор имени, пустой список, неизвестные поля, неверный тип/пустота версии и неподдерживаемые
params. В текущем варианте length и template не имеют параметров; params не игнорируются.

Эффект углубления — ошибка обнаруживается на старте вместо отказа первого пользовательского
запроса. Отрицательные конфигурации проверены параметризованным тестом
test_bad_configuration_rejected_at_startup. Разные сборки не делят изменяемое состояние.
При корректной конфигурации можно включить только length и задать другую config_version.

## 8. Воспроизводимость и ограничения

Пакет устанавливается через pyproject.toml; запуск имеет console script school-lab и
python -m school_lab. README содержит команды установки, тестирования, сборки и
обычной установки wheel в отдельном окружении. Файлы письменной защиты и данные включены
в исходный архив через MANIFEST.in. Wheel содержит исполняемый пакет; каталог data передаётся
как внешний аргумент и остаётся частью исходной поставки.

Проверена обычная установка wheel в новом окружении .venv-release с установленными runtime-
зависимостями, без editable-установки. Демонстрация запущена с ключом -I из /private/tmp:
импорт выполнен из site-packages этого окружения, получены 12 сдач и 24 отчёта,
original_preserved=true и same_service=true. pip check сообщил No broken requirements found.
Отдельный smoke-запуск wheel на Python 3.12.14 тоже прошёл; в этом дополнительном окружении
Pydantic предоставлен bundled runtime через system-site-packages. Это проверка совместимости
интерпретатора, а не вторая проверка чистого набора зависимостей. Факты сохранены в
docs/evidence/checks.json.

Известные ограничения:

1. Состояние теряется после завершения процесса, нет транзакций для конкурентного приёма.
2. Frozen-модели защищают обычные операции Python, но не создают изоляцию от доверенного
   плагина с правами процесса; проверка результата не является sandbox.
3. Анализаторы дают простые наблюдения, а не оценку корректности, авторства или плагиата.
4. Хеш привязан к принятой сериализации Python-проекта и исходному представлению даты.
5. Принятые до ошибки записи не откатываются; ограничение одной JSONL-строки не ограничивает
   общее число сохранённых работ в памяти.
6. Проверки используют фиксированный учебный корпус; результаты относятся к принятой
   версии схемы и указанным тестовым сценариям.

## 11. Интерпретация сквозного примера

При первом импорте `sub-001` получает устойчивый хеш версии. В сохранённом результате
LengthAnalyzer для этой работы отмечает одну непустую строку текста и три строки кода.
Evidence указывает строку 1 в `text` и строки 1, 3, 4 в `code`: пустая вторая строка
не считается непустой, но остаётся в исходной нумерации. Поэтому свидетельство можно
сопоставить с оригиналом без обратного пересчёта номеров.

Повторный импорт возвращает ранее сохранённые объекты. Изменение `text` при прежнем ID
даёт `conflict`; в результате demo дополнительно проверяются тождество сохранённого
объекта и неизменность его хеша. Если изменению назначить новый ID, оно станет отдельной
версией, а прежняя работа останется доступна.

Отчёт связывает наблюдение с работой через `submission_hash`, с заданием через `config_hash`
и с алгоритмом через ID и версию. Это позволяет отличить повторный запуск от анализа
другой версии. Сам отчёт не сохраняется в репозитории работ: демонстрация собирает его
в выходной JSON. Хранение истории отчётов в отдельном хранилище в текущий объём не входит.

В смешанном источнике последняя корректная работа принимается после трёх ошибок.
Это подтверждает частичный успех на уровне записей. Если чтение самого файла невозможно,
операция завершается ошибкой источника; корректные записи, принятые раньше, не откатываются.

## 12. Объяснение свойств Python

Аннотация типа описывает ожидаемый интерфейс для разработчика и статического анализатора.
Она не запрещает передать неверный объект во время выполнения. Pydantic проверяет внешний
вход, доменный конструктор — собственные инварианты, а `validate_report` — результат плагина.
Эти проверки расположены на разных границах и защищают разные операции.

Поверхностная копия отделяет контейнер, сохраняя ссылки на вложенные объекты. `deepcopy`
в источнике в памяти отделяет также вложенные входные значения. Frozen dataclass запрещает
обычное присваивание полей, но не замораживает произвольный вложенный список. Поэтому
доменный граф содержит frozen-объекты, строки и кортежи; список требований из DTO
преобразуется в `tuple`.

Protocol задаёт доступные операции, но не доказывает их смысл. Два источника могут иметь
одинаковый метод `open` и по-разному вести себя при повторном чтении. Контрактные тесты
проверяют это поведение отдельно от статической совместимости. Для `StreamSource`
политика чтения с текущей позиции и владения чужим потоком оговорена явно.

`break` завершает цикл, а генератор может оставаться живым, пока существуют ссылки на него.
Освобождение файла в проекте связано с выходом из контекстного менеджера, а не со сборкой
мусора. Источник закрывает и handle, и итератор; внешний поток `StreamSource` остаётся
у своего владельца.

Наконец, количество строк характеризует размер входа. Оно не проверяет алгоритм, выполнение
требований или происхождение текста. По этой причине LengthAnalyzer возвращает объяснение
и `score=null`, а не числовую оценку качества.

## 13. Границы технических выводов

185 успешных тестов подтверждают перечисленные сценарии в зафиксированном окружении.
Покрытие ветвей не означает проверку всех комбинаций значений и не заменяет анализ
контрактов. Измерение импорта характеризует конкретный участок обработки в памяти;
его нельзя переносить на сетевой сервер или файловый импорт целиком.

Проверка конфигурации при старте сокращает число поздних отказов, но не гарантирует
успешность каждого будущего анализа. Результат плагина всё равно проверяется после вызова.
Неизменяемость и SHA-256 обеспечивают связь с содержимым версии в принятой модели доверия,
но не являются цифровой подписью и не подтверждают автора.

Эти границы согласованы с назначением работы: готовая воспроизводимая основа приёма и
анализа с явными контрактами, проверенными ресурсами и заменяемыми компонентами.
