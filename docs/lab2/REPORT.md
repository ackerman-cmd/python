# ЛР 2. Анализ сходства и оценка качества

Траектория **Backend, основной уровень**. Этап А: потоковый импорт JSONL,
токеновый baseline и сервис поиска. Этап Б: второй метод, оценка качества,
сравнение полного перебора с индексом. Промежуточное состояние отмечено
тегом `lab-2-stage-a`.

## Реализация

Адаптеры ЛР 1 читают JSONL по одной записи и проверяют её схему. CLI сохраняет
допустимые сдачи в репозитории ЛР 1, после чего передаёт их в независимый
`ComparisonService`. Сервис также принимает генератор напрямую: так работает
нагрузочный сценарий, где исходные тексты не остаются в репозитории. Команда
обрабатывает корректные записи в смешанном файле и возвращает код 1, если
были ошибки строк; при невозможности анализа или запуска возвращает 2.

- `token-jaccard-1`: `tokenize`, без комментариев, отступов, переводов строк
  и других служебных токенов. Используются уникальные 3-граммы значимых
  токенов; между исключёнными блоками шаблона окно прерывается. Оригинальные
  имена и литералы сохраняются, поэтому переименование может уменьшать балл.
- `ast-jaccard-1`: берём множество сигнатур узлов с типами дочерних узлов и
  скалярными полями. Имена функций, классов, аргументов и переменных получают
  номера в порядке первого появления при обходе AST. Строки и числа
  сохраняются; атрибуты и имена импорта не переименовываются. Простая
  нормализация не учитывает области видимости, не проверяет семантику
  и может как сближать независимые работы, так и пропускать переписывания.
  Узлы, целиком находящиеся в шаблоне, исключены; диапазоны оставшихся
  структурных узлов могут охватывать несколько строк.
- Оба метода используют Jaccard: количество общих признаков, делённое на
  размер объединения. Пустое объединение или неразбираемый код дают
  `score: null`; синтаксическая ошибка содержит диагностическую строку.
  Код разбирается как текст и не исполняется. Для общих признаков остаётся
  диапазон первого появления на каждой стороне, соседние диапазоны
  объединяются. Точные совпадения с разрешённым шаблоном возвращаются
  отдельными диапазонами, с исходной нумерацией от 1.
- Кандидаты — сдачи того же задания от других студентов. Для самого запроса
  и его версий других баллов нет; версии перечисляются отдельно. При равном
  балле порядок определяется идентификатором, `null` идёт после нуля.
  Кеш признаков использует SHA-256 сдачи и SHA-256 конфигурации задания,
  включающей версию метода. Выдача дополнительно фиксирует версию схемы,
  версию конфигурации, порог и версию индекса.
- Индекс `shared-features-1` сопоставляет паре «задание, токеновая 3-грамма»
  идентификаторы сдач. Объединение списков даёт только кандидатов с общей
  3-граммой. Их балл вычисляется тем же Jaccard. В полном поиске один запрос
  перебирает до `n - 1` работ, попарный перебор всего задания — до
  `n(n - 1)/2`. Основная память — уникальные признаки со строками
  по всем сдачам, метаданные и, для индекса, ссылки на сдачи в списках.
  Потоковое чтение исключает загрузку файла целиком, но кеш и индекс растут
  с суммарным числом признаков. Инкрементальное обновление не заявлено.

## Корпус и оценка

68 синтетических сдач, 90 пар: по 45 в `tune` и `eval`, в каждом по 24
производных и 21 независимой паре, включая 6 пар с одним общим шаблоном.
`data/lab2/provenance.jsonl` хранит `family_id`, `assignment_id`, вариант,
происхождение и идентификатор родителя; `pairs.jsonl` хранит
`derivation_relation` и `template_only`. Основной корпус моделирует учебное
задание с выбором способа агрегации; отдельное задание изолирует общий шаблон.
Все идентификаторы вымышленные. Проверка останавливается при пересечении
семейств, паре разных заданий или недействительных ссылках.

Для каждого метода порог выбирается только на `tune`: максимальный F1
среди наблюдавшихся положительных баллов и 1, при равенстве выбирается больший
порог. На `eval` он зафиксирован. Неопределённость считается отсутствием
сигнала, но выводится отдельно; в этом корпусе все неопределённые пары
негативные. Полные результаты и баллы каждой пары: [quality.json](quality.json).

| Метод | Порог | TP | FP | FN | TN | Precision | Recall | F1 | Неопределённость |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| Токены | 0,4167 | 16 | 3 | 8 | 18 | 0,842 | 0,667 | 0,744 | 6/45 (13,3%) |
| AST | 1,0000 | 18 | 0 | 6 | 21 | 1,000 | 0,750 | 0,857 | 1/45 (2,2%) |

Разбор ошибок и пограничных случаев на `eval`:

1. `minimum-original / minimum-rename` — пропуск токенов (0,300).
   Переименование меняет несколько пересекающихся окон; AST сохраняет 1,0.
2. `negative-squares-original / negative-squares-rewrite` — оба метода
   пропускают производную: около 0,09 и 0,22. Генератор заменён комбинацией
   `map/filter` с промежуточной переменной, поэтому и структура изменилась.
3. `count-odd-original / positive-count-original` — ложный сигнал токенов:
   около 0,64. Формы генераторов похожи, но операции и происхождение разные;
   AST с порогом 1 эту пару не отмечает.
4. `eval-template-0-template-only / eval-template-3-template-only` —
   без настройки общий импорт даёт ложный сигнал с баллом 1,0. С известным
   шаблоном остаётся `null`; evidence шаблона — строка 1 каждой сдачи.

## Измерения

Сценарий нагрузки: одно задание, короткие искусственные сдачи, 64 группы
с общими признаками и четыре уникальных запроса. Seed 20261115; 16 запросов
на корпус, `k=5`, по 3 повтора на размер и режим. Конкурентность не
использовалась. Время включает потоковое чтение, валидацию, получение признаков,
сборку индекса (если включён) и серию запросов; эти стадии также приведены
отдельно. Пиковая память измерена `tracemalloc` в отдельных повторах,
чтобы трассировка не искажала время. Это пик выделений Python, а не RSS.
Среда: Windows 11, AMD64, Python 3.13.1, Pydantic 2.14.1. Исходные
замеры и медианы: [benchmark.json](benchmark.json).

В каждой ячейке сначала полный перебор, затем индекс:

| Записей | Построение, мс | 16 запросов, мс | Всего, мс | Пик, МиБ | Сравнения | Ускорение запросов | Recall всех / положительных |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 100 | 13,50 / 12,95 | 4,25 / 0,66 | 17,74 / 13,64 | 0,32 / 0,44 | 1 584 / 14 | 6,40× | 17,5% / 100% |
| 1 000 | 121,62 / 127,92 | 31,69 / 2,56 | 153,30 / 130,73 | 3,29 / 3,56 | 15 984 / 203 | 12,35× | 75% / 100% |
| 5 000 | 618,21 / 661,91 | 179,97 / 6,13 | 792,26 / 668,04 | 16,44 / 17,46 | 79 984 / 961 | 29,36× | 75% / 100% |

Recall кандидатов измерен как доля совпавших идентификаторов с полным
`top-k`. Индекс сохраняет все положительные результаты, но пропускает нули
и неопределённые баллы. На другом составе заданий ускорение изменится:
частые 3-граммы расширяют списки кандидатов, а при одном запросе затраты
на построение индекса могут не окупиться. Отдельный профиль `cProfile`
для 5 000 записей показывает, что при построении доминируют извлечение
признаков и валидация, при поиске без индекса — вычисление Jaccard.

## Воспроизведение и защита

Из корня, в окружении Python 3.12+ с установленным проектом:

```bash
python scripts/lab2/make_corpus.py
python scripts/lab2/evaluate.py
python scripts/lab2/benchmark.py --profile
python -m pytest -q --cov=school_lab --cov-branch
python -m ruff check src tests scripts
python -m ruff format --check src tests scripts
python -m mypy src scripts
```

Профиль сохраняется локально в `artifacts/lab2/full-5000.prof`. Сравнение
одной и той же пары до и после регистрации разрешённого шаблона:

```bash
python -m school_lab similarity data/lab2/submissions.jsonl eval-template-0-template-only --assignments data/lab2/assignments-without-template.json --config-version 1 --top-k 3
python -m school_lab similarity data/lab2/submissions.jsonl eval-template-0-template-only --assignments data/lab2/assignments.json --config-version 2 --top-k 3
```

Для `eval-template-3-template-only` в первом отчёте балл 1,0 и
`review_required: true`; во втором `score: null`, отмечен разрешённый
шаблон, изменены `config_version` и `config_hash`. Приложение не
устанавливает нарушение. Простой корпус не отражает разброс реальных
студенческих решений, а пары одного семейства взаимозависимы: эти метрики
нельзя переносить на реальных студентов. Результаты проверок:
[JUnit](tests.xml), [покрытие](coverage.json).

Итоговый прогон на Windows: 200 тестов, 99,31% суммарного покрытия;
Ruff, форматирование, mypy и проверка зависимостей прошли.
Собраны исходный архив и wheel; команды защиты проверены отдельно.
